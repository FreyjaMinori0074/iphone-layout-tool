# LLM 布局方案的接入设计

状态：架构研究与后续实现约定；尚未调用外部模型，也没有上传应用清单。
前置基础：原生布局的一次真机写入、核对与恢复已完成，见 [链路记录](END_TO_END.md)。

## 模型负责什么

模型根据用户目标提出候选布局、分组理由和权衡，本地程序负责检查和执行。
设备标识、组件配置 ID、wire payload、配对资料和 App 完整元数据都不应成为模型修改对象。
特别是 Installation Proxy 的完整元数据包含许多与布局无关的 SDK 字段，没有必要发送给模型。

输入应由本地导出器建立独立设计视图：

- 设备容量与网格；不需要 UDID、序列号等设备身份信息。
- 每个可编辑实例的 opaque ref、显示名、对象类型、页面顺序、组件尺寸及文件夹成员。
- App 分类由用户或可解释的本地规则提供；不要把模型猜测的类别当成设备事实。
- 用户的固定项、使用习惯、单手操作偏好、每页密度和组件保留要求。
- 是否允许改变 Dock、文件夹、页面及资源库归属。
- 坐标证据不足时明确 positions_unknown，不伪造原有留白。

设计视图在本地可预览。是否发送给哪个模型供应商、发送哪些字段，需要在实际接入时由用户选择。
当前阶段只定义格式和本地接口，不安装模型 SDK 或寻找 API Key。

## 模型输出的合约

推荐让模型输出“目标布局中的现有对象引用”，另附理由。
本地编译器将目标排列编译成受约束的操作，不让模型直接生成 plist 或设备命令。

示意（不是当前 CLI 已支持的完整设计导入格式）：

```json
{
  "schema_version": 1,
  "design_view_fingerprint": "exported-view-fingerprint",
  "title": "日常与出行分开",
  "dock": ["ref-001", "ref-002", "ref-003", "ref-004"],
  "pages": [
    {"items": ["widget-001", "ref-005", "folder-001"], "reason": "保留日程，常用应用集中"}
  ],
  "rationale": ["固定日历组件", "把临时使用的 App 留在后页"]
}
```

不能只检查 JSON 能否解析。完整输出需能说明每个现有引用的去向：保留、移动、进入资源库或用户允许的移除。
组件类型、尺寸和配置是受保护数据；模型只引用组件，不改造它的内部结构。
同一个 App 的多个实例必须有不同引用。模糊名称、失效 ref 和不存在的 App 都应被拒绝。

## 本地校验与比较

1. 校验输入视图指纹，确认模型方案不是基于旧桌面。
2. 验证引用存在、唯一、覆盖率，以及用户固定约束。
3. 用真实组件占位形状验证可放置性；仅用占位格数不能证明形状可排列。
4. 保留不能修改的组件对象，生成实际 wire 变化并重新计算资源库策略。
5. 展示页面预览、差异和理由，允许用户编辑草案；图片预览不足以证明可执行。
6. 用具体设备和最新读取结果编译设备计划，沿用已有 token、写入、核对和事务记录。
7. 记录结构验证、配置标识验证与人工视觉验证，分别报告。

评价指标可以包括：硬约束违反数、页面数量、首屏常用项覆盖、文件夹深度、用户确认过的触达区域、
相对于原布局的变更数量。没有用户使用数据时，不假装知道每个 App 的真实频次。

## 建议的实现顺序

1. 增加本地设计视图导出器及匿名 ref 映射，先不联网。
2. 将当前仅支持一次同页 swap 的操作语言扩展为移动、文件夹操作和受保护组件引用，补足页面形状校验。
3. 支持手工导入结构化方案，完成“方案文件 → 本地校验 → 差异 → 设备计划”的离线回归。
4. 先做两个小范围方案，例如只整理后几页、保留前三页组件与 Dock，比较可用性。
5. 再接用户选定的 LLM；供应商适配与设计合约分离，不把模型输出直接交给执行器。

第一轮真机成功只建立了执行基础，不代表上述多页设计、模型方案导入或模型连接已经完成。
